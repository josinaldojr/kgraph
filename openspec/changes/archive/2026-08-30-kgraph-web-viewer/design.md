## Context

`kgraph` today is a one-shot CLI: `build`/`update` write to a per-repo SQLite database (`modernc.org/sqlite`, WAL mode, a single `db.SetMaxOpenConns(1)` connection per process — see `internal/store.Open`), and `context`/`search`/`summarize` read it back for a single invocation and exit. The archived `kgraph-mvp` design explicitly deferred a daemon/server ("no persistent MCP server in this MVP... a natural v2, not built here") and explicitly called Web UI a non-goal for that change. This change builds that deferred v2: a long-running `kgraph serve` that visualizes the graph and stays live as `build`/`update` runs alongside it.

Two existing facts materially shape the design:
- `build_meta(repo_path, last_commit, last_build_at)` is a single row per repo, and `last_build_at` is bumped by both `build` and `update` (`Store.SetLastCommit`). It's already the cheapest possible "did anything change" signal — no new schema needed for change detection.
- Summaries are keyed by `(node_id, level)` where `level` is `node`/`file`/`module`. `node`-level summaries attach to real graph node IDs (`Struct`/`Interface`/`Function` today). `file`-level summaries are keyed by a **file path string**, not a graph node ID — there is no `File` node type in the graph; "file" is a grouping implied by `Node.File`, not a first-class entity. `module`-level summaries are keyed by the `Package` node's own ID (`graph.PackageID`) — so `Package` nodes already have a note today, aggregated from their files' summaries. This is a real point of confusion the UI needs to hide from the person browsing: a Package's note and a File's "note" both exist, but come from different corners of the schema.

## Goals / Non-Goals

**Goals:**
- `kgraph serve [--addr :8080]` starts an HTTP server that renders the graph as an interactive, force-directed node-link diagram in the style of Obsidian's graph view (global graph of everything, local graph centered on a selected node, hover/click highlighting, zoom/pan), reflects new `build`/`update` output without a restart, and never writes to the database.
- Every `Struct`, `Interface`, `Function`, `Package` (existing), and now `Table`, `Endpoint`, `ExternalDependency` (new) has a note visible in the UI, with a clear "no note yet" / "note is stale" state for anything not yet summarized — reusing the existing `stale` flag rather than inventing a new one.
- The server is read-only against the store: it must coexist safely with a concurrently running `build`/`update` process on the same database file.
- No new frontend build tooling: a single Go binary embeds its own static assets via `go:embed`.

**Non-Goals:**
- Replicating every Obsidian graph feature — no 3D view, no custom color groups by saved query/tag, no per-vault graph settings persisted server-side. The target is the core interaction model (force-directed layout, global/local modes, hover/click highlighting, zoom/pan, type-based color/filtering), not pixel parity with Obsidian's settings panel.
- Editing the graph, notes, or triggering `build`/`update`/`summarize` from the UI — `serve` is a viewer, not a control plane for the CLI. (A "trigger update from the browser" button is a natural, separately-scoped follow-up.)
- Multi-repo / multi-database views in one server instance — one `kgraph serve` instance serves one `--repo`/`--db`, matching every other `kgraph` command's scoping.
- Individual notes for `Field`/`Column` nodes (explicit product decision — see proposal).
- Real-time collaborative viewing (multiple browser tabs are fine; there's no per-viewer state to synchronize beyond the shared read-only graph).
- Authentication/access control — `serve` binds to localhost by default, like a local dev server; exposing it beyond localhost is the operator's choice and explicitly out of scope for this change to secure.

## Decisions

**1. Read-only store access via a second `sql.DB` opened without exclusive assumptions, not a new store type.**
`Store.Open` today assumes single-writer-per-process (`SetMaxOpenConns(1)`, WAL). `serve` adds a `store.OpenReadOnly(dbPath)` that opens the same WAL-mode database but is documented and used strictly for reads. WAL's one-writer/many-readers model already supports a second process reading while `build`/`update` writes; the only discipline required is that `serve`'s code path never calls an `Exec` that mutates `nodes`/`edges`/`summaries`/`build_meta`. Alternative considered: give `serve` its own `Store` with full read-write API and just "not call the write methods" — rejected because it leaves a footgun (a future contributor adding a write-triggering feature to `serve` wouldn't hit a compile-time or structural barrier).

**2. Change detection: poll `build_meta.last_build_at`, not filesystem watching.**
A goroutine queries the single `build_meta` row every ~2s (cheap, single-row, indexed by primary key). On change, it reloads the full graph (`LoadGraph`) and the full `summaries` table into memory and diffs against what's currently held, then pushes a `graph-updated` event over SSE to connected browsers, which trigger a re-fetch. Alternatives considered: `fsnotify` on the `.db`/`.db-wal` files (rejected: WAL checkpointing and SQLite's own file-handling make raw filesystem events noisy and harder to reason about than one indexed row read) and a full WebSocket push of the diffed graph (rejected for v1: SSE is simpler and unidirectional, which is all this needs — the browser already has `SearchNodes`-backed lookups for anything more targeted).

**3. In-memory graph stays loaded between requests; reload is triggered only by the poller, not per-request.**
Every `context`/`search` CLI invocation today calls `loadGraphAndStore` fresh because it's a one-shot process. `serve` is long-running, so it loads the graph once at startup and keeps it in memory, refreshed only when the poller (Decision 2) detects a change — avoiding a full `LoadGraph` SQL round-trip on every HTTP request. Request handlers read the in-memory graph directly; only the poller touches the database on a timer.

**4. Frontend: server-rendered JSON API + a single embedded HTML page with vanilla JS + `<canvas>`, no framework or bundler.**
Consistent with the rest of the module's minimal-dependency posture (no cgo, no external graph library, no embeddings) and with the explicit product request to match Obsidian's graph view: nodes are circles positioned by a force simulation (mutual repulsion between all nodes, edges act as springs pulling connected nodes together, mild centering force so the graph doesn't drift off-canvas), rendered and animated on `<canvas>`. Node radius scales with degree (edge count); node color encodes `NodeType` (`Package`, `Struct`, `Interface`, `Function`, `Field`, `Table`, `Column`, `Endpoint`, `ExternalDependency` each get a distinct color, matching Obsidian's type/tag color groups). Hovering a node highlights it and its direct neighbors (full opacity) while dimming everything else, mirroring Obsidian's hover behavior; clicking a node pins the view into **local graph mode** (Decision 4a) and opens the node detail panel (existing requirement, unchanged). The canvas supports scroll-to-zoom and drag-to-pan, and dragging a node repositions it and lets the simulation settle around the new position, all standard Obsidian graph interactions. The frontend subscribes to `/events` (SSE) for live refresh and calls a small JSON API (`/api/graph`, `/api/graph/local?id=&hops=N`, `/api/node?id=`, `/api/search?q=`) that thinly wraps `graph.Graph`, `store.SummariesByLevel`/`GetSummary`, and the existing `SearchNodes`. Node IDs travel as query parameters rather than path segments: this graph's deterministic IDs (`graph.EndpointID`, file paths, import paths) routinely contain `/`, `:`, and spaces, which don't survive as a single `net/http` path-wildcard segment. Alternatives considered: React/Vite with a charting library (D3-force, Cytoscape.js, react-force-graph) — rejected as disproportionate and as the first npm build step in an otherwise Go-only module; a naive O(n²) repulsion pass per animation frame is fine at the node counts a single Go repo's `Struct`/`Interface`/`Function`/`Table`/`Endpoint` population realistically produces (low thousands), so no need for a spatial-partitioning force library. SVG/DOM-per-node (rejected in the original draft of this decision) was reconsidered and dropped in favor of canvas once the requirement became "hundreds of nodes animating every frame" — DOM reflow at that scale is the wrong tool; canvas is what Obsidian itself uses for the same reason.

**4a. Global graph vs. local graph mode, reusing the existing hop-based BFS.**
Obsidian's graph view has two modes: the global graph (everything) and a local graph centered on the currently-open note, expanding N hops out. `internal/context`'s BFS (built for `GetContext`'s subgraph expansion) already does exactly the traversal a local graph needs — it just needs to return node/edge IDs for rendering instead of (or in addition to) a token-budgeted rendered string. `/api/graph` returns the full graph (nodes + edges) for global mode; `/api/graph/local?id=&hops=N` reuses the same BFS (exported as `context.LocalGraph`) to return the subgraph around one node for local mode, defaulting `hops` the same way `context` does. Selecting a node from search or from the global graph switches to local mode centered on it; a visible "back to global graph" control returns to the full view.

**5. File and Package "notes" are surfaced through the node detail panel, not as their own graph nodes.**
Files aren't graph nodes and won't become graph nodes in the force-directed view either — inventing a synthetic `File` node purely for visualization would misrepresent the actual graph structure `SearchNodes`/`GetContext` operate on, and Obsidian's "note = node" mental model doesn't map cleanly here (a `kgraph` "note" is a generated summary of a code entity, not a file a person wrote). Instead, a `Struct`/`Function`'s detail panel shows its file path and links to that file's aggregated summary as a breadcrumb/side fact, and `Package` nodes (which already carry their own note via the existing module-level aggregation) appear directly in the graph like any other node. Alternative considered: promote files to real `graph.Node`s — rejected as a much larger, unrelated change to `internal/graph`/`internal/parser` for a purely presentational need.

**5a. Type filters, not hierarchical drill-down, control what's visible.**
The earlier draft of this design used a Package→File→entity drill-down tree as the primary navigation. Replaced by Obsidian-style toggle filters (one per `NodeType`, e.g. hide `Field`/`Column` by default since they're the most numerous and least summarized, show `Table`/`Endpoint`/`ExternalDependency` on demand) layered on top of the single global force-directed graph, plus the search-to-local-graph flow from Decision 4a for targeted navigation. This keeps one coherent graph view (matching the product ask) instead of two different UI paradigms (tree + graph) competing for the "primary" view.

**6. `Table`/`Endpoint`/`ExternalDependency` join `summarizableTypes`, each with a type-specific source-text renderer.**
`internal/summarizer.summarizableTypes` (currently `Struct`/`Interface`/`Function` only) gains these three types. `pendingNodes` already reads a node's own text via `readSourceLines` for existing types; the new types have no Go source span to read, so `pendingNodes` gains a small per-type source-text builder: `Table` → column list (name and type, where the parser recorded one) plus incoming `references_fk` edges; `Endpoint` → HTTP method and path (decoded from its deterministic ID) plus the handler function's signature via its `exposes_endpoint` edge; `ExternalDependency` → module path from `Properties`, plus a declared version when the extractor happens to have recorded one (it doesn't always). `Field`/`Column` are deliberately left out of `summarizableTypes` (unchanged) per the proposal's scope decision.

## Risks / Trade-offs

- **[Risk]** Two OS processes (`serve` reading, `build`/`update` writing) against one SQLite file is new territory for this codebase — the archived design's only concurrency risk callout was about two *writers* racing, not a reader alongside a writer → **Mitigation**: WAL mode is specifically designed for this; `serve`'s read path is isolated behind `store.OpenReadOnly` so it structurally cannot become a second writer; the poller's `LoadGraph` reload is a plain read query, safe to run against a mid-write database (it will see either the pre- or post-transaction state, never a torn one, per SQLite's WAL guarantees).
- **[Risk]** Polling every ~2s means up to ~2s of staleness between an `update` finishing and the UI refreshing → **Mitigation**: acceptable for a human-paced workflow (a developer isn't watching the exact millisecond a background `update` lands); the interval is a constant, easy to tune later if it proves too slow or too chatty.
- **[Risk]** Reloading the entire graph into memory on every detected change could get expensive for very large repositories → **Mitigation**: out of scope to optimize now — `LoadGraph` is already the same full-reload path every one-shot CLI command uses today, so this isn't a new cost class, just a new caller; revisit with incremental in-memory patching only if a real repo's reload time becomes user-visible.
- **[Risk]** A naive O(n²) force simulation redrawn every animation frame could get sluggish once a repo's node count climbs into the thousands (e.g. `Field`/`Column` nodes, which are the most numerous type) → **Mitigation**: type filters (Decision 5a) default `Field`/`Column` to hidden, keeping the typically-rendered node count well below where naive repulsion becomes visibly slow; local graph mode (Decision 4a) is also a natural escape hatch since it only renders a small hop-bounded subgraph. Revisit with a spatial-partitioning force library only if real usage shows the global view itself (with filters on) is too large to animate smoothly.
- **[Risk]** Adding three new summarizable types changes what `summarize pending` emits, which could surprise an existing provider-driven summarization workflow expecting only `Struct`/`Interface`/`Function`/`File`/`Package` entries → **Mitigation**: purely additive (new `type` values in the JSON output), and `summarize apply`'s hash-validation logic is unchanged — a provider that ignores unfamiliar `type` values loses nothing it had before.
- **[Risk]** No auth on `serve` means anything that can reach the bound port can browse the whole code graph, including summaries → **Mitigation**: default bind to `localhost`; documented as a local developer tool, not a hosted service, matching the CLI's existing trust model (no API keys, no network calls by default).

## Open Questions

- Should `kgraph serve` also expose the existing `GetContext` (`context` command's token-budgeted render) as an API endpoint for programmatic use, or is the node-detail panel's simpler summary+relations view sufficient for v1? Leaning toward deferring `GetContext` exposure — it's designed for AI-provider token budgets, not a human reading a page — but worth revisiting if the viewer turns out to double as a context-copy tool.
- Exact SSE reconnection/backoff behavior on server restart isn't specified yet — default browser `EventSource` auto-reconnect is likely sufficient but should be verified during implementation.
