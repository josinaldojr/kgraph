## Context

The Java, TypeScript, and Python extractors (`internal/parser/{java,typescript,python}/parser.go`) are 100% regex-based by a deliberate, already-reverted decision (see `openspec/changes/archive/2026-09-13-multi-language-support/design.md`: tree-sitter was tried, required CGO, and was rejected in favor of keeping the whole build cgo-free — same reason `internal/store` uses `modernc.org/sqlite`). That decision stands; this change works within it rather than reopening it.

The Go extractor (`internal/parser/go/`) is the reference implementation for two of this change's patterns: `ExtractPackages` does real scoped extraction via `golang.org/x/tools/go/packages.Load(cfg, patterns...)`, and `imports` edges to `ExternalDependency` nodes are derived from actual `import` statements classified as internal (`ex.internal[path]`, i.e. part of the loaded module) or external — never from a manifest's declared dependency list directly. `go.mod`'s own dependency list is not separately parsed into the graph at all. The other three extractors currently do the opposite for dependencies: they parse the manifest (`pom.xml`/`package.json`/`requirements.txt`/`pyproject.toml`) into standalone `ExternalDependency` nodes, and separately create `imports` edges from `import`-statement parsing that point at bare `Package` nodes for every target — including third-party libraries, which produces dangling, property-less `Package` stubs (e.g. Python `import flask` creates a `pkg:flask` node with no properties at all) instead of resolving to the `ExternalDependency` node the manifest parse already created for `flask`.

## Goals / Non-Goals

**Goals:**
- Bring `ExtractPackages`, Python's ABC/Protocol class handling, Java's `entityTableName`, and decorator/annotation-argument capture into conformance with already-accepted spec text (no spec changes needed for these).
- Add the two genuinely missing requirements the review identified: dependency nodes reachable via `imports` edges, and deterministic extension-count tie-breaking.
- Do this with one shared, pure-Go utility (balanced-paren/bracket scanner) rather than three divergent implementations.

**Non-Goals:**
- Reopening tree-sitter/WASM adoption — already decided against twice in the archived change; out of scope here.
- A typed `Language` field on `Node`, a typed `Confidence` enum, reversible IDs, or a coverage-percentage target — all deferred (P2 in the originating review); the first conflicts with `graph-model`'s deliberate choice to keep language in `Properties`, and the others are independent of the correctness bugs this change fixes.
- Perfect reconciliation between a manifest's declared dependency name and its actual import/require specifier (e.g. Python `PyYAML` importing as `yaml`, an npm scoped package's subpath imports, a Maven artifactId that doesn't match its Java package name). This is inherent to regex/manifest-based extraction without a language-specific resolver and is accepted as a best-effort limitation, consistent with how these extractors already treat call/inheritance resolution.
- Resolving pending cross-file edges (`extends`/`calls`/`implements`) whose destination lies in a file *outside* the current scoped-update's `patterns` — see Decision 3.

## Decisions

### Decision 1: One shared balanced-paren/bracket scanner in `internal/parser/common/`
Add a small function, e.g. `common.ScanBalanced(s string, start int, open, close byte) (content string, end int, ok bool)`, that scans forward from an opening delimiter to its matching close, tracking nesting depth (and, pragmatically, skipping over delimiters inside quoted strings, since decorator/annotation arguments routinely contain string literals like `"/users/{id}"`). All three extractors replace their `\(([^)]*)\)`-style capture groups (decorator args in Python, annotation args in Java, decorator args in TypeScript) and the Flask-specific `\[([^\]]*)\]` with calls to this scanner.

**Alternatives considered:**
- Fix each extractor's regex independently (three near-duplicate hand-rolled scanners) — rejected: the whole point of the review's P1-5 finding is that this pattern recurs identically three times; a shared utility is the same amount of code written once.
- A full expression tokenizer/mini-parser — rejected as over-engineering for what is still, deliberately, a best-effort regex extractor.

**Consequence for decorator parsing specifically**: Python's `parseDecorators` currently matches decorators line-by-line (`strings.Split(before, "\n")`), which cannot see a multi-line `@app.route(\n  "/x",\n  methods=["POST"],\n)`. The scanner-based fix operates on the *whole preceding text*, not a single line, so it naturally captures multi-line decorator arguments too — this is what actually fixes the Flask `methods=[...]` case the review flagged as P0, not just nested-parens.

### Decision 2: Python only creates a `Struct` node for a class after checking ABC/Protocol inheritance
Today `extractFile` calls `g.AddNode` for the `Struct` node unconditionally (line ~242), then — only if a parent is `ABC`/`Protocol` — calls `g.AddNode` again for an `Interface` node under the identical ID (`StructID`/`InterfaceID` share one format by design, per `graph-model`'s "Existing IDs unaffected" requirement — this is not being changed). The fix reorders the check: determine whether the class is ABC/Protocol-derived first, then create exactly one node (`Interface` or `Struct`), matching `python-extraction`'s literal "an Interface node is created *instead of* a Struct node."

**Alternatives considered:**
- Give `Struct`/`Interface` a discriminated ID scheme (what the original review literally suggested) — rejected: this directly contradicts two already-accepted requirements (`graph-model`'s "no existing... ID generator's output changes" and `multi-language-merge`'s "Intra-language type collision recorded" scenario, which treats a same-ID collision between different NodeTypes as an accepted, warned-and-resolved outcome for the genuinely-coincidental case, e.g. Java/TypeScript's separate `class`/`interface` regexes matching an unrelated same-named pair). Renaming the ID scheme would also silently change every existing Struct/Interface ID for all three languages, which is a much bigger blast radius than the actual bug (which is Python-specific and only affects the ABC/Protocol branch).
- Leave the `Struct` node creation in place and delete it via a new `Graph.RemoveNode` when the Interface branch fires — rejected: `Graph` has no removal API today (by design — see `graph.go`'s comment on `AddNode`'s last-write-wins semantics), and adding one just for this case is a bigger change than reordering four lines.

### Decision 3: `ExtractPackages` scoping — walk only the given directories; leave out-of-scope pending edges best-effort
`patterns` arrive from `internal/build/update.go` as directory strings (`"."`, `"./internal/foo"`), one per directory containing a changed file for that language — mirroring the Go extractor's package-granularity, not a recursive subtree match. The fix changes `filepath.Walk` in each of the three extractors to skip any file whose directory (relative to `repoPath`, slash-normalized) isn't in `patterns` (empty `patterns` → extract nothing, matching `extractor-interface`'s existing "Scoped extraction with empty patterns" scenario). `knownInternal` (already computed correctly by `common.KnownInternalForLanguage` and passed in by `update.go`) is used the same way Go's extractor uses it: to classify a reference as internal-to-the-repo vs external when creating dependency/import edges (see Decision 4), not to fetch node data from outside the walked scope.

**Known limitation, accepted**: a `pendingEdge` (extends/calls/implements) produced during a scoped walk whose destination lives in a file *outside* `patterns` will not resolve in that update pass, because `resolvePendingEdges` only looks up destinations in the graph just built (`g.Node(pe.dstID) == nil` → silently skipped) — this is the existing best-effort semantics already accepted for full extraction (a reference to an out-of-repo type is expected to be silently skipped), just now also applying to in-repo-but-unwalked-this-pass targets. The edge is recovered on the next full `kgraph build`. Making this fully correct would require `update.go` to merge `newSub` with the previously-persisted graph *before* resolving pending edges, which is a materially larger change to the update pipeline's data flow — tracked as an open question below rather than folded into this change.

### Decision 4: Classify import targets as internal/external when creating `imports` edges; point external targets at `ExternalDependency`
Mirrors Go's `ex.internal[path]` pattern exactly. Each extractor already builds (or, for Python, can cheaply build) a set of module/package identifiers it created `Package` nodes for during this walk, plus `knownInternal` for scoped updates. When resolving an `import`/`from ... import`/`require`/Java `import` statement's target:
- If the target matches an internal package/module → create the `imports` edge to that `Package` node (existing behavior, unchanged).
- Otherwise → create the `imports` edge to `graph.ExternalDependencyID(<name>)`, reusing the `ExternalDependency` node the manifest parse (`pom.xml`/`package.json`/`requirements.txt`/`pyproject.toml`) already created when the name matches, or creating one on the fly (tagged with the correct `language` property, per `multi-language-merge`'s existing per-node-type requirement) when it doesn't match any declared dependency — e.g. a language's own standard library, which Go's model already treats as `ExternalDependency` too.

This replaces today's behavior of creating a bare, property-less `Package` stub for every external import target, and is what actually connects the manifest-derived `ExternalDependency` nodes into the graph (the review's literal ask), rather than bolting on a synthetic edge from an artificial "project root" node.

**Alternatives considered:**
- Create one synthetic "project" node per manifest and edge every declared dependency to it, independent of whether any import statement actually references it — rejected: produces edges with no code-level justification (a dependency listed in `package.json` but never imported would still get an edge), and doesn't fix the existing dangling-`Package`-stub bug for third-party imports, which is the more visible symptom.

### Decision 5: `LanguageDetector.detectByExtension` breaks ties by a fixed language order
`detectByExtension`'s `for lang, count := range counts` is replaced with an iteration in a fixed, explicit order (the same priority order already used for marker detection: Go, Java, TypeScript, JavaScript, Python), selecting the first language whose count equals the running maximum. This makes the result reproducible across runs on an identical file tree without depending on Go's randomized map iteration.

### Decision 6: `graph.AddEdge` re-derives its adjacency index entry when an edge's endpoints change under a reused ID
Today, `if _, exists := g.edges[e.ID]; !exists { index }` skips re-indexing whenever `e.ID` was already present — correct when the same logical edge (same `Type`/`SrcID`/`DstID`, since `EdgeID` is derived from exactly those three) is re-added, but silently leaves `out`/`in` pointing at the *old* `SrcID`/`DstID` if a caller ever adds an edge under an existing ID with different endpoints. No extractor or merge path in this codebase does that today (verified: `EdgeID` is always computed from the same `SrcID`/`DstID` passed on the `Edge` struct). The fix compares the *existing* edge's `SrcID`/`DstID` against the incoming one and re-indexes if they differ, so the invariant holds even if a future caller violates the current convention. This is defensive hardening, not a fix for an observed defect — called out explicitly so it isn't mistaken for one during review.

## Risks / Trade-offs

- **[Risk]** The balanced-paren scanner's "skip delimiters inside quoted strings" handling adds a small amount of state-machine complexity for something that was previously "just a regex." → **Mitigation**: keep it to a single, well-tested ~30-line function in `common/` shared by all three extractors, rather than reimplemented per-extractor; unit-test it directly (unbalanced input, nested brackets, quoted delimiters, multi-line input) independent of any single language's fixtures.
- **[Risk]** Decision 4's internal/external classification can misfire for languages with indirect export/import conventions (e.g. a TypeScript barrel file, a Python package `__init__.py` re-export) — a reference might be misclassified as external. → **Mitigation**: same best-effort framing already accepted for `calls`/`extends` resolution in these extractors; no new failure mode, just extended to imports.
- **[Trade-off]** Decision 3 explicitly does not make scoped-update pending-edge resolution fully correct across the old/new graph boundary. → Accepted as an explicit, documented limitation (see Open Questions) rather than expanding this change's blast radius into `internal/build/update.go`'s core merge flow.
